# 基礎概念メモ（このリポジトリのどこに対応するか）

## クラウドの基本

| 概念 | 一言で | このリポジトリでの例 |
|---|---|---|
| IaaS / PaaS / SaaS | 自分で管理する範囲の違い（インフラから / アプリだけ / 何も管理しない） | S3 は基盤寄り、Glue・Athena・Bedrock はサーバー管理不要のマネージドサービス |
| サーバーレス | サーバーの起動・保守を意識せず、使った分だけ払う | Athena（クエリごと）、Glue ジョブ（実行時間ごと）、Bedrock（トークンごと） |
| リージョン / AZ | 地理的に独立したデータセンター群 / その中の物理的に分かれた拠点 | 全リソースを `ap-northeast-1`（東京）に作成。S3 は自動で複数 AZ に複製される |
| IAM ロール | サービスに「何をしてよいか」を渡す仕組み | 用途ごとに4つのロールを最小権限で定義（[architecture.md](architecture.md#7-iam-は用途ごとに分け最小権限)） |
| IaC | インフラをコードで定義して再現可能にする | `infra/cloudformation/` の4テンプレート。コンソールでの手作業を全部コード化 |

## データ分析基盤の用語

| 用語 | 意味 | 対応 |
|---|---|---|
| データレイク | 加工前のデータも含め、形式を問わず大量に置いておく場所 | S3 の `raw/`（生データ）と `curated/`（加工済み）を分けて保存 |
| データウェアハウス | 分析用に整理された構造化データを置く DB（例: Redshift） | 本構成では使わず、レイク上を Athena で直接クエリ |
| メタデータ | 「データについてのデータ」。列名・型・場所など | Glue Data Catalog のテーブル定義。**実データは S3 にあり、カタログには入らない** |
| スキーマ | テーブルの構造（列名と型） | Crawler が CSV から推論 |
| パーティション | データをフォルダ単位で分割し、関係ない部分を読まないようにする | `product_category=Books/` |
| 列指向フォーマット | 列ごとにまとめて保存する形式（Parquet, ORC） | 必要な列だけ読める → スキャン量削減 |
| プロファイル | データの統計（欠損・分布・外れ値）を把握すること | DataBrew のプロファイルジョブ。品質が悪いデータで判断しないための最初の一歩 |
| One-Hot エンコーディング | カテゴリ値を「該当すれば 1、それ以外 0」の列に展開 | `verified_purchase` → `verified_purchase_Yes / _No` |
| SPICE | Quick のインメモリエンジン。データを取り込んで高速に可視化 | Quick のデータセット作成時に選択 |
| プロンプト | 生成 AI への指示文。出力形式（JSON）まで指定すると後段で機械処理できる | `bedrock/analyze_reviews.py` の `PROMPT_TEMPLATE` |

## 「ギャップ」分析の考え方

★の数と本文のトーンが一致しているかを見る。「Negative＝悪い商品」ではない。

| ★ | 本文 | 意味 | 使い道 |
|---|---|---|---|
| 4〜5 | Positive | 素直な高評価 | — |
| 4〜5 | Negative | ★は高いが本文に不満 | ★の平均だけでは見えない**隠れた不満**。品質改善の材料 |
| 1〜2 | Negative | 素直な低評価 | — |
| 1〜2 | Positive | ★は低いが商品自体には好意的 | 低評価の原因が**商品以外**（配送・梱包・重複購入など）。物流や販売側の改善材料 |
| 3 | — | 中間なのでギャップ判定の対象外 | — |

★だけを集計すると「★1 が多い＝商品が悪い」と誤判断しうる。テキストを AI で構造化して★と突き合わせることで、改善すべき部署（商品開発か、物流か）まで切り分けられる、というのがこの分析のビジネス上の価値。
