### 1. 弁当自動盛り付けシステム（卒業研究）
**[`yamaha_scara-main/`](./yamaha_scara-main/yamaha_scara-main)**

食品製造業の人手不足・盛り付け工程自動化を目的に、YOLO + RGB-D カメラ + SCARA ロボットを統合したリアルタイム自動盛り付けシステムを開発。

| 項目 | 内容 |
|------|------|
| 動作環境 | Ubuntu 22.04 / ROS2 Humble / Python 3 / Intel RealSense D435 / Yamaha YK400XE |
| 推論モデル | YOLOv8-seg（インスタンスセグメンテーション）・YOLOv11（bbox検出） |
| 入力解像度 | 640×480px, 30fps（RGB＋Depth同期） |
| 弁当箱サイズ | 75mm × 100mm（実寸→カメラ距離からpixel換算） |

**処理パイプライン（7フェーズ）**

| フェーズ | 処理内容 | 処理時間比率 |
|----------|---------|------------|
| A | フレーム取得 + RGB-D アライメント | ~4.6% |
| **B** | **YOLO-seg 推論** | **~74%（ボトルネック）** |
| C | マスク領域の3D重心推定（中央値外れ値除去） | ~11% |
| D | 深度ソート（Z値昇順） | ~0.01% |
| E | 組み合わせ探索（最大C(8,4)=70通り、弁当箱収まり判定） | ~3.2% |
| F | OpenCV オーバーレイ描画 | ~6.4% |

**数値成果（高速化実験）**

| 手法 | avg FPS | avg Latency | 技術選定理由 |
|------|---------|-------------|------------|
| ベースライン | 11.2 FPS | 89.3 ms | — |
| 推論頻度削減（5fに1度） | 28.9 FPS | 42.0 ms | YOLO が74%を占めるため推論回数削減が最も効果的 |
| 解像度調整（640→480） | 10.9 FPS | 93.1 ms | 単独では効果薄（Depth処理のオーバーヘッドが相殺） |
| Step1+2 併用 | 31.2 FPS | 47.0 ms | 相乗効果を検証 |
| **bbox/seg ハイブリッド** | **31.8 FPS** | **34.4 ms** | 安定フレームはbbox（軽量）、不安定時のみseg使用（使用率4.2%）で精度を保ちつつ負荷削減 |

> **最終結果: 11.2 FPS → 31.8 FPS（約 2.85 倍）、レイテンシ 89.3ms → 34.4ms**

**技術選定理由**
- **YOLOv8-seg を採用した理由**: 食材は形状・大きさにばらつきがあり bbox 中心では把持位置がずれる。セグメンテーションマスクで食材の実領域を抽出することで、深度重心推定の精度を向上させた
- **RGB-D（Intel RealSense）を採用した理由**: 単眼 RGB のみでは密集・重なり状態での奥行き推定が困難。Depth センサで直接 Z 値を取得することで、遮蔽ロバスト性と推定精度を両立
- **itertools.combinations による全探索**: 候補数は最大8個（C(8,4)=70通り）と計算量が十分小さいため、近似探索より実装シンプルさと最適性保証を優先

### 2. 弁当盛り付け完全自動化 — 双腕 × 強化学習（修士研究 2026.4〜）

食品製造の盛り付け工程を **単腕 SCARA から双腕産業用ロボットへ拡張**し、
「双腕協調のふるまいを強化学習で創発させる」ことを主眼に据えた修士研究。
学部研究（食材認識・把持点推定）を土台に、認識精度向上と実機統合を進めている。

| 項目     | 内容                                                            |
| ------ | ------------------------------------------------------------- |
| テーマ    | 食材認識精度向上と産業用ロボットへの統合による弁当盛り付け工程の完全自動化                  |
| ロボット   | Yaskawa Motoman SIA5（双腕 / 7軸×2 + 6本指グリッパー、実質13DOF/腕）    |
| 動作環境   | Ubuntu / ROS2 / MoveIt2 / Isaac Sim 5.1 / Python 3.11 / C++    |
| 認識     | YOLOv8-seg（Roboflow データセット約3,000枚をセグメンテーション変換で拡充）        |
| 把持配置   | ① MoveIt2 古典経路計画（配置）② MAPPO 強化学習（双腕協調の創発、Phase 2）      |

**アプローチの二層構成**

| レイヤ        | 手法                          | 技術選定理由                                                        |
| ---------- | --------------------------- | ------------------------------------------------------------- |
| 配置（確定動作）   | MoveIt2 + OMPL/RRTConnect   | RL の試行錯誤を経て、静的な配置は古典経路計画の方が安定・再現性が高いと判断（Option B） |
| 双腕協調（創発動作） | MAPPO（CTDE）on Isaac Sim     | 動的ゴールの協調は経路計画が苦手で、双腕の協調タイミング創発は RL の独壇場と整理           |
| 把持局所制御     | PPO（単腕）                     | Phase 2 双腕 MAPPO の土台。単腕を古典手法で解くと双腕協調に繋がらないため RL で構築  |

**数値成果（強化学習）**

| フェーズ            | 内容                          | 結果                                       |
| --------------- | --------------------------- | ---------------------------------------- |
| ベースライン          | ランダム方策 500ep               | 平均報酬 **−6.1**                            |
| Phase 0（学習機構検証） | 双腕・同役割で学習ループ検証（≈930ep）  | 平均 **47.6** / 最大 130（約186,200 timesteps） |
| Phase 1（単腕把持）   | PPO で唐揚げ把持ポリシー学習          | **把持成功率 100%**（v7 モデル）                   |

**技術選定理由**

- **MoveIt2 と RL を役割分担した理由**: MAPPO v1–v13 の検証で「静的配置は RL より古典計画が安定」と定量的に判断。確定動作は MoveIt2、創発が要る双腕協調のみ RL に振り分けた
- **CTDE（MAPPO）を選んだ理由**: 双腕は「集中学習・分散実行」が本質。各腕が相手の退避を待たずに進入する等の協調は、独立学習（IPPO）では創発しづらい
- **potential-based reward shaping を使った理由**: 距離の変化量を報酬にすることで最適方策を壊さずに接近行動を誘導。反比例ボーナスのみだと「動かないのが得」の均衡に陥る問題を回避
- **非対称タスク設計（左腕=パスタ/右腕=唐揚げ）**: 柔軟体と剛体で役割を分け、クレーター成形・オーバーラップ進入・一方向巡回退避という創発メカニズムを狙う設計にした

### 3. Yamaha SCARA Robot ROS2 制御パッケージ
**[`yamaha_scara-main/`](./yamaha_scara-main/yamaha_scara-main)**

九州工業大学 Hayashi Lab の Yamaha YK400XE 向け ROS2 制御パッケージ群。2025年9月より始動。

| 項目 | 内容 |
|------|------|
| 動作環境 | Ubuntu 22.04 / ROS2 Humble / Yamaha RCX340 コントローラ |
| ロボット | Yamaha YK400XE（4軸 SCARA、最大可搬重量 4kg） |
| 通信方式 | Ethernet（TCP/IP）経由で RCX340 にオンラインコマンド送信 |
| 制御モード | 関節値制御（J1/J2/J4: 度、J3: mm）・標準座標制御（x,y,z,θ） |

**実装済み機能**

| 機能 | 実装パターン | 技術選定理由 |
|------|------------|------------|
| PC–ロボット通信（ブリングアップ） | ROS2 Launch ファイルで一括起動 | 複数ノードを毎回手動起動するコストを排除 |
| GUI コントロール（関節値） | tkinter スライダー + ROS2 サービス呼び出し | ROS2 ネイティブ GUI ライブラリがないため、Python 標準の tkinter で依存を最小化 |
| GUI コントロール（標準座標） | 同上、エンドエフェクタ(x,y,z,θ)指定 | 関節値計算不要でタスクレベルの直感的操作を実現 |
| 真空ピック＆プレイス | ROS2 Service（`/set_vacuum`）で ON/OFF | サービス呼び出しにより任意のノードから真空制御を再利用可能にした |
| HAYASHI LAB 文字描画 | P/L/C モーション + Arch 動作、PointCloud2 配信 | 軌跡を Rviz で可視化することで動作の事前確認と安全性確認を実現 |

**技術選定理由（ROS2 全般）**
- **ROS1 でなく ROS2 を選択した理由**: DDS ベースの通信で LAN 越しの分散ノード構成に対応。Yamaha 社提供の ROS1 ドライバを ROS2 移植したベースリポジトリ（yk400xe_ros2）が存在し、これを活用
- **推奨動作速度を30%以下に制限している理由**: 高速 + 大変位の組み合わせで振動・転倒リスクがあるため、安全マージンとして明示的にドキュメント化

### 4. UN Trade AI — RDTII Regulatory Analysis Demo
**[`UN-AI-Hackathon-2026-main/`](./UN-AI-Hackathon-2026-main/UN-AI-Hackathon-2026-main)**

UN主催「Global Hackathon on AI for Digital Trade Regulatory Analysis」提出作品。  
各国の法令文書をAIで自動収集・解析し、UN基準（RDTII Pillar 6/7）へマッピングするRAGシステムのフロントエンド。

| 項目 | 内容 |
|------|------|
| 動作環境 | Node.js 18.17以上 / npm 9以上 / ブラウザ（Chrome/Firefox/Safari） |
| 対応言語 | 英語 / 日本語（URL: `/en/...` ↔ `/ja/...`） |
| 対象データ | 5カ国（日本・タイ・ケニア・シンガポール・ブラジル）の法令文書 |
| API設計 | FastAPI差し替えを想定した REST 設計（`BASE_URL` 環境変数で切替） |

**実装パターン**

| 画面 | 実装パターン |
|------|------------|
| ダッシュボード | `GET /api/stats` → StatsCard コンポーネントで KPI 表示 |
| 法令検索 | クエリパラメータ（country / pillar / language / q）で JSON フィルタリング |
| AI 監査ビュー | 引用スニペット左・元文書右の分割レイアウト、Approve/Flag ボタン |
| Pillar マッピング | 国×Pillar の対応状況テーブル、CSV エクスポート |

**技術選定理由**
- **Next.js 14 App Router を採用した理由**: ハッカソンの短期間（数日）で i18n・API・UI を一気通貫で実装できる。Pages Router より Server Components による型安全な fetch が直感的
- **shadcn/ui を採用した理由**: Radix UI ベースでアクセシビリティが保証済み。コンポーネントをソースコピーして管理するため、本番環境でのバンドルサイズ最適化が容易
- **next-intl を採用した理由**: URL ベースのロケールルーティング（`/en/` `/ja/`）を middleware 1ファイルで実現でき、審査員が任意の言語でデモを確認できるようにした
- **モックデータで FastAPI 差し替え対応設計にした理由**: ハッカソン期間中はバックエンドが未完成でも審査可能なデモを提供しつつ、実運用時の差し替えコストを最小化するため

### 5. 九州爬虫類フェス 2026 — 非公式ファンサイト
**[`reptiles/`](./reptiles)**

2026年5月30〜31日開催「九州爬虫類フェス 2026」の非公式ファンサイト。

| 項目 | 内容 |
|------|------|
| 動作環境 | 任意のモダンブラウザ（ビルドツール不要、HTML単体で動作） |
| データ規模 | 167店舗（エリアブース95 + テーブルブース72） |
| 外部依存 | Google Fonts のみ（CDN 1リクエスト） |
| ファイル構成 | 単一 HTML ファイル（HTML + CSS + JS を完全内包） |

**実装パターン**

| 機能 | 実装パターン | 数値 |
|------|------------|------|
| キーワード検索 | `Array.filter()` で `name / tags / desc` を横断検索 | 167件をタイプごとに即時絞り込み（ブロッキングなし） |
| フィルター | エリア別・注目・地元・グッズの4軸を `AND` 条件で組み合わせ | 最大4条件の複合絞り込み |
| モーダル | `display: none / block` 切替 + ESCキー・背景クリックで閉じる | ライブラリ0依存 |
| スクロール連動ナビ | `window.scrollY` 監視でヘッダースタイルを動的切替 | スクロール閾値 50px |
| アニメーション | CSS `@keyframes` のみ（フェードイン・シマー・スウェイ） | JS アニメーションなし |

**技術選定理由**
- **Vanilla JS / ゼロ依存を選択した理由**: イベント当日に現地でファイルを渡す想定のため、npm install や CDN 障害のリスクをゼロにする必要があった。単一 HTML ファイルでオフライン動作を保証
- **フレームワーク（React/Vue 等）を使わなかった理由**: 167件のフィルタ・検索程度の処理は Vanilla JS の `Array.filter()` で十分高速。仮想 DOM のオーバーヘッドを避け、初期ロードを最小化
- **データ収集に AI（Claude）を活用した理由**: 公式サイトの167店舗をスクレイピング → チラシ写真の OCR → SNS 検索という3段階を手動で行うと数十時間かかる作業を、AI ツール活用で大幅に短縮

### 6. Vlog Maker App
**[`Vlogapp/`](./Vlogapp)**

動画素材・テキスト台本を入力すると、自動でナレーション付きVlog動画を生成するStreamlitアプリ。

| 項目 | 内容 |
|------|------|
| 動作環境 | Python 3.x / Streamlit / VOICEVOX エンジン（localhost:50021）/ Windows or Linux |
| 音声生成 | VOICEVOX HTTP API（`/audio_query` → `/synthesis`）、話速スケール調整対応 |
| 動画処理 | MoviePy（VideoFileClip・AudioFileClip・CompositeVideoClip） |
| キャッシュ | 音声: SHA-256（テキスト + speaker_id + speed_scale）、シーン: 音声ハッシュ + 全パラメータ |
| 並列処理 | `concurrent.futures` によるシーン単位の並列レンダリング |

**実装パターン**

| 機能 | 実装パターン | 技術選定理由 |
|------|------------|------------|
| 音声生成 | VOICEVOX REST API に `audio_query` → `synthesis` の2段階 POST | 無料・ローカル完結・日本語品質が高い。OpenAI TTS は有料かつ外部送信が発生するため非採用 |
| フリガナ処理 | `*漢字*\|よみ` 記法を正規表現で音声用・表示用に分離 | 台本にルビを埋め込むだけで読み上げ精度を改善できる独自記法 |
| キャッシュ戦略 | パラメータ全体の SHA-256 でファイル名を生成し `temp_uploads/` に保存 | シーン内容が変わっていなければ再レンダリング不要。パラメータ変更を自動検知 |
| 並列レンダリング | `concurrent.futures.ThreadPoolExecutor` でシーン単位に並列化 | MoviePy の I/O バウンド処理は GIL の影響が小さくスレッド並列が有効 |

| 平均レイテンシ | **34.4 ms** | ベースライン比: 89.3ms → 34.4ms（61%削減） |
| seg 使用率 | 4.2% | 安定フレームは bbox のみ使用、不安定時のみ seg |
| YOLO 処理時間比 | ~74% | 7フェーズ中のボトルネック |
| 信頼度閾値 | 0.25 | CONF_TH = 0.25 |
| 外れ値除去 | 中央値 ± 0.02m | Z_OUTLIER_TH = 0.02m |
